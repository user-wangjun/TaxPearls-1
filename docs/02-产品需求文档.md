## 一、产品概述

### 1.1 一句话定位

> 面向企业财务、代理记账机构与财税职业院校的**可解释税务风险识别引擎**——同一审计内核，支撑企业检查与仿真实训。

「可解释」是定语，不是形容词：每一条风险线索都必须能展开为原始数值或关系证据、来源、计算/判断过程、规则及适用依据、建议核查事项。不是所有规则都有“两个金额”；无法取得证据不能补造。审计报告用于发现问题和检查盲区，不作违法认定，也不宣称已经解决税务风险。

### 1.2 要解决的问题

| 对象 | 真实痛点 | 现状做法 | 本产品的解法 |
| --- | --- | --- | --- |
| 财税专业教师 | 风险审计课无真实案例可讲，只能用教科书例题 | 手工编案例，无标准答案 | 由规则库反向生成带标注题库，题题有据 |
| 财税专业学生 | 只会背条文，不会查账；实习才第一次见真账 | 靠实习碰运气 | 沙箱内做仿真账套审计，自动评分 + 漏检/误报明细 |
| 企业财务 | 本企业账税材料分散，手工核对繁琐 | 逐表检查、依赖经验 | 上传本企业材料，确认范围后得到风险线索、证据与判断限制 |
| 代账机构会计 | 单人管多户，风险排查靠经验、靠抽查 | Excel 手工比对，覆盖不全 | 管理多家客户，每次导入一家企业的多份材料，输出风险清单 + 证据卡 |
| 代账机构负责人 | 质量问题无法量化，出事了才知道 | 事后补救 | 风险留痕 + 复核轨迹，把质量变成可管理的指标 |

### 1.3 产品目标

按期次拆解，每期只承诺一件事：

| 期次 | 产品目标（一句话） | 达成标志 |
| --- | --- | --- |
| **P0** | 证明「一条规则怎么判、怎么举证」 | 上传一张 Excel，页面上看到完整证据链 |
| **P1** | 证明「一次完整审计怎么做完」 | 20–30 条规则跑完，出报告，学生能答题打分 |
| **P2** | 证明「五大能力全貌成立」 | 多源接入 + 关联方图分析 + 出题器 + 多租户 |

### 1.4 边界：明确不做的事

边界越清楚，越有说服力。企业使用场景与商业获客分开；其余能力边界如下：

| # | 不做 | 理由 |
| --- | --- | --- |
| 1 | 不因支持企业自用而自动开展直销、收费或获客 | 2026-09-27 已确认企业自用功能；商业渠道另定，旧直销限制不再作为企业功能禁令 |
| 2 | 面向税务机关的监管侧产品 | 与「服务小微企业」定位冲突，政务采购不可触达 |
| 3 | 自训模型、承诺准确率数字 | 不可举证，审计场景容错率为零 |
| 4 | 对接真实税务系统（生产环境） | 合规风险与实施成本双高；RPA 仅在沙箱内模拟 |

> **对「准确率」的正式口径**：不承诺准确率数字。对外统一表述为——
> 「内置 N 条可溯源风险规则，每条给出触发明细与法条依据，支持人工复核。」
> 前者一碰即碎，后者越问越硬。

### 1.5 成功度量

**P0 度量（唯一）**

- [ ] 给一张符合模板的 Excel 审计材料，在 Web 页面上（非命令行）能看到至少 1 条风险的完整证据卡
- [ ] 证据卡上的每个数值都能追到「哪个科目编码 / 哪张申报表哪一栏」
- [ ] 材料不足时，该规则显示「未执行 + 原因」，**不得**静默显示为「通过」

**P1 度量**

- [x] 规则库 ≥ 20 条，三大比对类型（内部勾稽 / 外部交叉 / 指标偏离）全覆盖
- [x] 一次完整审计从上传到出 PDF 报告 ≤ 5 分钟（单户、单期；本机自动化回归）
- [ ] 学生作业自动评分与教师人工评分的一致率 ≥ 90%（同批样本实测）

**P2 度量**

- [ ] 发票、银行流水、社保三类外部数据可接入并参与规则求值
- [ ] 关联方图规则可命中「同一实控人控制的多家企业间异常交易」类风险
- [ ] 出题器可由 1 条规则反向生成 1 套带标准答案的题目

## 二、用户与角色

### 2.1 目标用户

| 市场 | 角色定位 | 说明 |
| --- | --- | --- |
| **财税职业院校** | **主线** | 赛道为职教赛道，评审天然偏好「赋能职业教育」；学校有真实教学场景、教师与学生可试点，是唯一能拿到真实反馈与真实数据的地方 |

| **学生** | 院校 | 在仿真账套里练查账 | 领题、查账、标注风险点、提交、看评分明细 |

| **会计** | 代账 | 快速排查手上客户的风险 | 导入材料、看风险清单、复核、导出报告 |

## 三、产品架构与核心概念

### 3.1 一套内核，两个出口

```
        ┌──────────────────────────────────────────────┐
        │      可解释税务风险引擎（唯一内核）             │
        │  ┌──────────────┐   ┌──────────────┐         │
        │  │   识别层       │   │   解读层      │         │
        │  │  确定性规则引擎 │   │   LLM         │         │
        │  │  （可举证）     │   │  （可读性）     │         │
        │  └──────────────┘   └──────────────┘         │
        └──────────────────────────────────────────────┘
                     │                    │
          ┌──────────┴─────────┐   ┌──────┴───────────┐
          │   院校实训沙箱       │   │   代账作业台       │
          │ 出题 → 查账 → 评分   │   │ 导入 → 排查 → 报告  │
          └────────────────────┘   └──────────────────┘
```

### 3.2 识别与解读分离（核心技术原则）

| 层 | 技术 | 职责 | 硬约束 |
| --- | --- | --- | --- |
| **识别层** | 确定性规则引擎（YAML 声明 + 求值） | 判定是否命中风险，产出数值与证据 | **绝不用 LLM 做风险判断。** 审计场景容错率为零，LLM 幻觉无法举证 |
| **解读层** | LLM | ① 把命中的规则翻译成业务人员能看懂的话；② 生成报告文字段落；③ 实训场景中的问答式讲解（充当「带教师傅」） | 只能改写已判定的事实，**不得新增、不得推翻判定结论** |

> 解读层的输出必须可被溯源：LLM 生成的每段话都要能指回具体的 Finding。禁止 LLM 自由发挥补充未经计算的风险点。

### 3.3 审计与出题互为逆运算

```
审计模式（正向）：真实账套 ──→ 规则引擎 ──→ 风险清单（带证据）
出题模式（反向）：目标规则 ──→ 规则引擎 ──→ 带标注题库（带标准答案）
```

**规则库是唯一真相源。** 出题器读取规则的 `inputs` 与 `threshold`，反向构造能命中（或刻意不命中）该规则的数据，即可自动生成题目与标准答案。同一份规则定义，两个执行方向，**无需另建题库系统**——这是产品结构上的白送能力。

### 3.4 输出三层结构

**企业审计的主输出（2026-09-27 已确认）**：发现的问题与待核查线索、已完成的检查与结论、仍无法判断的事项；各项关联原始证据、规则依据及补充/核查建议。`hit/pass/skipped` 是检查明细，不代替业务结论；命中不等于违法，未发现异常不等于全面无风险，未执行不算通过。报告标明企业/税号/主期间、材料范围和版本；网页、导出、核验和提问围绕同一结果展开。系统“处理完成”不等于企业风险已整改，不设置没有后续事实依据的“已解决问题”统计。以下层次仍用于呈现证据和教学，不改变上述目的。

| 层 | 面向 | 内容 | 缺了会怎样 |
| --- | --- | --- | --- |
| **警示层** | 经营管理者 | 风险等级（高/中/低）+ 一句话结论 | 用户不知道该先看哪条 |
| **证据层** | 会计、教师 | 指标值 + 计算过程 + 偏离度 + 法条依据 + 建议动作 | **产品变成黑盒，价值归零** |
| **实训层** | 学生、教师 | 漏检项 + 误报项 + 得分明细 + 标准答案 | 实训退化为「答案对不对」的判分器 |

### 3.5 术语表

| 术语 | 定义 | 注意 |
| --- | --- | --- |
| 标准指标 | 由原始科目 / 申报项聚合而来、规则引擎唯一识别的内部口径量（如「营业收入」） | 规则只认标准指标，不认原始科目 |
| 标准化 | 把各财务软件不一致的科目编码与期间口径，统一映射为标准指标的过程 | **最脏也最核心的一步，是隐藏护城河** |
| 条件规则 | YAML 声明的 if-then 字段比对 / 阈值判定 | 占规则库约 90% |
| 图规则 | 基于节点与关系网络的模式匹配（关联方、关联交易） | 占约 10%，**独立引擎，不与 YAML 混用** |
| 证据卡 | 一条风险的完整举证单元 | 产品核心资产 |
| Finding | 一条规则的执行结果，状态为 hit / pass / skipped | `skipped` 不等于 `pass` |
| 全电发票（数电票） | 本身即结构化电子数据，可从电子税务局批量获取 | **不需要 OCR** |
| 四流一致 | 合同流 / 发票流 / 资金流 / 货物流的一致性校验 | P2 能力 |

**FR-B06/B07/B08 —— 三类比对的规则落点**

所有风险来源可归为三类比对，规则库按此组织，**不存在第四类**：

| 类型 | 定义 | 是否需要外部数据 | 代表规则 |
| --- | --- | --- | --- |
| **内部勾稽** | 账内自洽性，仅凭企业自身材料校验 | 否 | R-001 收入未足额申报；R-002 增值税账申勾稽不符 |
| **外部交叉** | 账面 vs 外部真实数据（金税四期核心逻辑，最有说服力） | 是 | R-004 个税社保人数不匹配 |
| **指标偏离** | 横向（同地区同行业）/ 纵向（同比环比）对标 | 需行业基准值 | R-003 增值税税负率异常 |

**FR-B09 —— 图规则与条件规则的边界（重要，易错）**

> ⚠️ **不要把「YAML 条件规则」与「图查询」混为一谈。**
> - 条件规则是 **if-then 求值**：「利润表收入 比 申报销售额 高 10% 以上」—— 与图无关。
> - 图规则是 **关系网络遍历**：「找出 A 的股东 → 这些股东控制的其他公司 → 它们之间的交易」。

**知识库隔离原则（2026-09-26 定案）**

现有系统的"知识"分三层，**结构上不存在跨客户混淆面**：

| 层 | 范围 | 隔离机制 |
| --- | --- | --- |
| 规则库 | 平台级共享 | 税法规则对全平台一致属设计意图；规则版本冻结进各次审计，历史不受后续变更影响 |
| 审计证据图谱 | 单次审计 | `build_graph()` 只从该次审计的冻结数据集与 Finding 构建，一审计一图 |
| AI 问答 / 解读 | 单审计作用域 | 无状态调用，模型上下文仅含当前图谱邻域证据；无向量库、无跨审计语料、无会话记忆 |

> ⭐ **长期设计原则（未来若增设跨审计知识库 / 经验库时强制执行）**：
> **一客一库**——知识库按客户建档、挂 `client_id`，**检索禁止跨客户**；
> 权限复用客户档案的会计指派关系，不另造访问控制；
> 删除按 `client_id` 边界执行（满足《数据安全法》删除义务，客户终止合作即整库可删）；
> 跨客户经验沉淀**必须人工脱敏后升入平台经验层**（独立选题，未实施，未经脱敏严禁自动聚合）。
> 场景说明：一家会计机构服务多个企业客户由客户档案覆盖（FR-G07），一个用户处理多客户时知识库仍按客户分开建档。

**FR-E04 —— 评分设计的关键要求**

评分标准本身的合理性，**是教师认可度的关键**。三条硬要求：

1. **有标准答案，且答案来自规则库**（不是人工编的），保证答案与审计引擎口径一致
2. **误报要扣分，但必须解释**「为什么它不构成风险」——否则学生无法从错误中学习
3. **不设「全对才算过」**，按风险点分别计分，让部分正确也有正反馈

> 学生查出的风险点与出题时注入的风险点，是同一份规则库的两个方向。**出题与评分天然自洽**，这是架构带来的优势，不是额外工作量。

### 5.3 规则 YAML 规范

**必填字段**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | str | 唯一，格式 `R-xxx` |
| `name` | str | 规则名称（业务语言） |
| `category` | str | 分类：收入完整性 / 税会勾稽 / 指标偏离 / 外部交叉 / … |
| `tax_type` | str | 税种：增值税 / 个人所得税 / 企业所得税 / … |
| `severity` | enum | `high` / `medium` / `low` |
| `logic` | map | 求值定义（见下） |
| `evidence` | list | 需要展示的指标清单，**让「可举证」成为规则固有属性** |
| `legal_basis` | list | 法条依据 |
| `suggestion` | str | 建议动作 |

**可选字段**：`description`（规则说明，供教师/会计理解）

**2.0规则包新增必填字段**：`version`（规则版本）、`inputs`（指标→取数口径/来源映射）、
`scope`（适用范围）、`threshold_basis`（阈值出处）、`references`（官方直接链接）。
分类统一为内部勾稽/外部交叉/指标偏离；公式依赖、inputs、evidence必须一致。
实际格式及迁移说明见 `03-核对规则目录与使用说明.md`，旧示意YAML需补齐元数据。

**三种 logic 类型**

| type | 判定 | 参数 |
| --- | --- | --- |
| `deviation` | `\|left − right\| / \|right\| > threshold` | `left` `right` `threshold` |
| `amount_mismatch` | `\|left − right\| > tolerance` | `left` `right` `tolerance` |
| `ratio_range` | `numerator / denominator` 落在 `[min, max]` 之外 | `numerator` `denominator` `min` `max` |

补充：三种基本类型可通过`all.conditions`组合；操作数支持`add/sub/mul/div/min/max`白名单公式。
比率及相对偏离分母须大于零，否则未执行；金额采用Decimal，阈值等值不命中，区间为闭区间。

**设计要点**：每条规则自带 `evidence` 与 `legal_basis`。会计/教师可参与编写规则，**无需写代码**——这是规则库能持续扩张的组织前提。

### 5.4 证据卡规范（产品核心资产）

每条命中风险必须可展开为如下结构：

```
风险类型：收入未足额申报
风险等级：高
命中规则：R-001 账面收入 vs 增值税申报销售额相对偏离度 > 10%
触发明细：
  营业收入                   1,280,000.00   ← 主营业务收入 + 其他业务收入（本期贷方发生额）
  增值税.销售额                860,000.00   ← 增值税申报表—销售额
  绝对差额                    420,000.00   （计算值）
  相对偏离度                      48.84%   阈值 10.00%
计算过程：|1,280,000.00 − 860,000.00| ÷ |860,000.00| = 48.84%，阈值 10.00%
法条依据：《中华人民共和国增值税法》第三条、第七条
          《中华人民共和国税收征收管理法》第二十五条、第六十三条
          《中华人民共和国会计法》第九条
建议动作：核查账面收入与申报销售额的差异构成，逐笔比对是否存在未开具发票但已实现的收入、
          应视同销售的业务，以及跨期确认问题。若属已实现收入未申报，应及时更正申报并补缴
          税款及滞纳金。
```

**硬要求**

| # | 要求 | 理由 |
| --- | --- | --- |
| 1 | 每个数值必须标注**取数来源** | 否则无法追到原始凭证，等于不可举证 |
| 2 | 必须展示**计算过程**，而非只给结果 | 评委/教师会追问「这个 32.8% 怎么来的」 |
| 3 | 必须给出**阈值与依据** | 说明「为什么 32.8% 算异常，10% 不算」 |
| 4 | `skipped` 必须显式展示 | 缺数据不等于无风险，隐藏此状态即失职 |

### 8.5 与原型（`prototype/`）的差距

原型**仅可用于对齐产品形态，不可作为技术基线**。落地需重构的部分：

| 项 | 原型现状 | 落地要求 |
| --- | --- | --- |
| 角色 | 5 个（含「税务机关」） | 砍「税务机关」，4 个业务角色另加平台管理员（见 2.2） |
| 数据 | `mockData` 内存态，刷新即丢 | 需持久化（FR-G04） |
| AI | 关键词匹配本地文本，无模型调用 | 需真实规则引擎 + LLM 解读层 |
| 评分 | `Math.random()` | 需可解释的评分标准（FR-E04/E05） |
| 解析 | 上传控件仅读文件名与大小 | 需模板导入 + 字段映射（FR-A01/A02） |
| 鉴权 | 密码硬编码 `123456`，角色由下拉框决定 | 需真实鉴权与权限隔离（FR-G05/G06） |
| 安全 | 全量 `innerHTML` 拼接用户输入 | 需输入转义（FR-F11） |
| 空壳 | 批改/批量/规则配置/用户管理按钮无事件 | 需按 FR 逐项实现 |
| 报告导出 | 仅 `alert`，未生成文件 | 已由 `src/render.py` 实现，需接入 Web |
